# 数値の出所 — 画面の数字は、どの元テーブルのどの列から、どのロジックで作られているか

ダッシュボード（ボード・企業ページ・スカウト未利用の登録ページ）に出る件数・人数・求人数・日付が、BigQuery のどの生テーブルのどの列を、どう結合・絞り込み・重複排除・集計して作られているかを 1 か所にまとめる。
式の一覧は [指標定義](./指標定義.md)、画面要素 → API → マート列の対応表は [データ紐付け](./データ紐付け.md)。この文書はその 2 つが書いていない「元テーブルの列」と「マートの中のロジック」を埋める。

- マートの実装は `bq/marts/scheduled_query.sql`（本文の「ステップ 05」などはこのファイルのコメント番号）。Worker 側の計算は `src/worker/services/*.ts`、ブラウザ側の計算は `src/shared/metrics/*.ts` と `src/app/features/*/`。
- 表名・列名はコードの綴りのまま書く。値の例は書かない（実データは画面か BigQuery で見る）。
- 数字の式やマートのロジックを変えたら、この文書も同じ PR で直す（`CLAUDE.md`）。

## 1. 読み方と前提

### 1.1 更新のタイミングと「日付」

| 用語 | 定義（`scheduled_query.sql` の DECLARE） |
|---|---|
| 更新 | 毎日 22:45 UTC = **07:45 JST** に `scheduled_query.sql` を 1 本実行し、`cms_*` を作り直す。Worker はマートだけを読み、次回 08:30 JST まで Cache API に持つ |
| `run_date` | 実行日（JST）。「今日」。契約状態・契約残日数・当月の掲載求人数はこの日で判定 |
| `data_date` | `run_date − 1`。イベント（スカウト・応募・閲覧・ログイン）はこの日まで。Aurora → BQ の日次ロードが前日分までのため |
| `cur_month` | `run_date` の月初。当月は MTD（`data_date` まで） |
| `window_start` | `cur_month − 13 か月`。マートの月次は **13 か月 + 当月 = 14 か月** だけ持つ。画面の「直近 13 か月」はこの窓 |
| `fact_start` | `cur_month − 25 か月`。スカウトだけはこの範囲まで読む（契約開始からの累計送信 `scout_sent_contract_to_date` 用） |

### 1.2 企業の紐付け（profile → company）

実績（求人・閲覧・応募・スカウト）はすべて **プロファイル単位** のテーブルにあり、企業単位にまとめるには `profile_id → company_id` の対応が要る。

| 項目 | ロジック |
|---|---|
| 対応表 `pcm`（ステップ 01） | `company_profiles_full`（全プロファイル。2026-10-29 に `company_profiles` から変更）の `DISTINCT profile_id, company_id`（両方 NOT NULL）。**RA（`profile_id` 4928 / 14508）・RDS（7080）は除外** |
| 結合 | 実績の各テーブルを `profile_id` で `pcm` に JOIN して `company_id` を得る。1 社に日本語・英語など複数プロファイルがあっても 1 社に寄せる |
| プロファイルが無い企業 | `companies` にはあるが `company_profiles_full` に 1 行も無い企業は、枠数は出るが実績は 0 のまま、企業種別は「不明」になる（2026-10-29 に全件表へ切り替え、求人未掲載の契約企業も対象に入った） |

### 1.3 対象企業（ステップ 02 `companies_now`）

元テーブル `companies`（企業単位、日次フルリロード）から次の条件で絞る。ここで落ちた企業はマートに入らず、ボード・企業ページ・KPI・ベンチマークのどこにも出ない。

| 条件 | 列・ロジック |
|---|---|
| 契約期間がある | `active_from IS NOT NULL` |
| WAWW を除く | `NOT REGEXP_CONTAINS(UPPER(publishing_sites), 'WAWW')` |
| Network 契約を除く | `id NOT IN (SELECT company_id FROM dm_network_contract_candidates WHERE company_id IS NOT NULL)` |
| 社内テストアカウントを除く | `id NOT IN (5542, 8980, 7277, 7196)`、`internal_name` に「レジュメ更新自動リクエスト専用」を含まない |
| 窓に重なる | `active_from <= run_date + 30 日` かつ `COALESCE(active_to, 9999-12-31) >= window_start`（契約中 + 直近に終了 + 開始間近） |
| RA / RDS を除く | `company_profiles_full` で `profile_id IN (4928, 14508, 7080)` を持つ `company_id` を除外 |

契約状態は同じ CTE で決める。

| 列 | ロジック |
|---|---|
| `is_contracted_now` | `active_from <= run_date <= COALESCE(active_to, 9999-12-31)` |
| `contract_state` | `ending_30d`（契約中かつ `active_to − run_date <= 30`）→ `active` → `ended_recent`（終了後 90 日以内）→ `ended` → `upcoming`（`active_from > run_date`） |
| `days_to_contract_end` | `DATE_DIFF(active_to, run_date, DAY)`。`active_to` が NULL なら NULL（画面は「無期限」） |

### 1.4 画面で「契約中」として数える企業

マートには終了直後・開始前の企業も入る（ベンチマークの母集団のため）。画面では次で絞る。

| 場所 | ロジック |
|---|---|
| Worker `companyMasterQuery` | `WHERE company_type != 'NW'`（NW はボード・登録ページに出さない） |
| Worker `loadBoardCore` | `contract_state ∈ {active, ending_30d, upcoming, ended_recent}` または選択月の `is_contracted_in_month = TRUE` の企業だけ応答に含める |
| ブラウザ `isContracted`（`src/shared/metrics/board.ts`） | **当月**: `contract_state` が `active` か `ending_30d`。**過去月**: `cms_company_monthly.is_contracted_in_month` |
| `is_contracted_in_month`（ステップ 11 `contracted_m`） | `companies.active_from <= LAST_DAY(month)` かつ `COALESCE(active_to) >= month`、または `cms_contract_snapshot_daily`（毎朝の契約状態の写し）でその月のどこかの日に `is_contracted = TRUE` |

### 1.5 企業種別・契約体系・枠数・担当

| 画面の値 | 列 | ロジック |
|---|---|---|
| 種別 | `cms_company_master.company_type` | ステップ 02 の CASE。(1) `companies.internal_name` または主プロファイルの `company_name || profile_name` が `daijob\s*agent`（NFKC・小文字）に一致 → **DA**。(2) プロファイルの `company_type` が `'直接'` またはプロファイル無し、かつ 求人枠 0 / NULL かつ当日の掲載 0（`active_jobs` を set_id で数えて 0）かつ スカウト枠 0 / NULL かつ当月送信 0（`scouts.sent_at >= cur_month` が無い）→ **NW**。(3) それ以外は主プロファイルの値: `rpo_contract = TRUE` → RPO、`company_type` が `'直接'` → 直接、`'派遣'` → 派遣、他 → 紹介。プロファイル無し → 不明 |
| 主プロファイル | `company_profiles_full`（1 profile = 1 行。同点は `profile_id` 最小） | 同じ企業の複数プロファイルのうち `active_jobs` の掲載求人数（`COUNT(DISTINCT COALESCE(set_id, job_id))`）が最多、同数なら `recorded_on` が新しいもの。企業名・業種・`contract_type` はこの順で 1 件取る |
| 企業名 | `cms_company_master.company_name` | 主プロファイルの `company_profiles.company_name`。無ければ `companies.internal_name` |
| 契約体系（KPI の内訳・企業名の黄色） | Worker `contractKindOf`（`src/worker/services/boardService.ts`） | `company_profiles.contract_type` が `'広告掲載型'` → 広告掲載、`'採用成功報酬型'` → 成功報酬。無ければ `plan_name`（SF 契約の `ServiceName__c` → 成立商談の `ServiceName__c` → `contract_type`）を NFKC・小文字にして `成果報酬|採用成功|人材紹介|rpo|cf` → 成功報酬、`dj|wa` → 広告掲載。どちらも無ければ不明（内訳に入れず合計だけ） |
| 求人枠・スカウト枠 | `cms_company_master.job_posting_limit` / `scout_limit` | `COALESCE(companies.job_posting_limit, MAX(company_profiles.job_postiong_limit), MAX(company_profiles_all.job_postiong_limit), 0)`。スカウトは `companies.resume_bank_scout_limit` → `company_profiles.resume_bank_scout_limit` → `company_profiles_all.resume_bank_scout_limit` → 0。企業単位の契約値を優先し、複数プロファイルは SUM ではなく MAX。D1 `company_settings.job_limit_override / scout_limit_override` があればそれで上書き |
| CS 担当 | `cms_company_master.cs_owner_name_default / cs_owner_email_default` | `owner_source = 'sales_staff'`: `active_companies.sales_staff`（`company_id` ごとに `recorded_on` 最新）。メールはローマ字「姓 名」から `名の頭文字-姓@daijob.com` を導出（姓だけなら NULL）。DA の企業は名前 `'DA'`・メール NULL に固定。D1 `company_settings.cs_owner_email / cs_owner_name` があればそれが勝つ。画面は `surname()` で苗字だけ表示 |
| 担当=自分 | Worker `mergeCompany` | 上の担当メール（小文字）がログインメールと一致 |
| アカウント種別（企業ページの切替・ボードの `+種別`） | `cms_company_master.account_types / accounts_json` | ステップ 01 `pcm.account_type` = プロファイルの `company_profiles_full.company_type`（直接 / 紹介 / 派遣）。1 企業の全プロファイルを種別ごとにまとめ `直接,紹介` の順（ステップ 02 `company_accounts`）。実績の種別別は `cms_company_monthly` の `account_type` 行（§4） |
| 業種（ベンチマークの群） | `cms_company_master.industry` | 主プロファイルの `company_profiles.industry`（空・`(未選択)` は無視）→ 無ければ SF `sf_accounts.industry0413__c` を `cms_dim_industry_alias` で DJ 表記に正規化 → `(未設定)` |

## 3. ボード（`/`）

API `GET /api/board?month=`（`src/worker/routes/board.ts` → `boardService.ts`）。表示・集計はすべて §1.4 の「契約中」の企業だけ。月は窓の 14 か月から選ぶ（既定 = 当月）。

### 3.1 KPI タイル（`kpiStrip`、`src/shared/metrics/board.ts`）

| タイル | ロジック | 元の列 |
|---|---|---|
| 契約企業 | 契約中の企業数（§1.4） | `cms_company_master.contract_state`、`cms_company_monthly.is_contracted_in_month` |
| アクティブ企業数（最終ログイン 30 日以内） | 契約中のうち `login.daysSince !== null && daysSince < 30` | `cms_company_login.days_since_login` = `DATE_DIFF(data_date, MAX(login_date), DAY)`（§6.6） |
| スカウト利用社数（利用率） | 契約中のうち選択月の送信数 `> 0` の社数。括弧は ÷ 契約中の社数 | `cms_company_monthly.scout_sent` |
| スカウト消化率 | 契約中で `scout_limit > 0`（枠の期間が「月」）の企業について Σ `scout_sent` ÷ Σ `scout_limit` | `cms_company_monthly.scout_sent`、`cms_company_master.scout_limit`（D1 上書きあり） |
| 各タイルの内訳（広告掲載 / 成功報酬） | 同じ計算を契約体系（§1.5）ごとに行う。不明は内訳に入れず合計だけ | Worker `contractKind` |
| 色（スカウト利用社数） | 利用率 < 50% 赤、< 70% 黄 | — |
| 色（スカウト消化率、当月のみ） | 消化率 ÷ 営業日消化率 が < 0.8 赤、< 1 黄。営業日消化率 = 当月の経過営業日（`data_date` まで）÷ 営業日数（`src/shared/calendar/jp-holidays.json`、年末年始 12/29〜1/3 を除く） | `meta.bizDays` |

### 3.2 表の列（`BOARD_COLUMNS`、`CompanyBoard.tsx` の `cellText`）

|---|---|---|---|

| 担当 | 苗字（未設定は「未設定」） | `cms_company_master.cs_owner_name_default`（D1 上書き優先） | `active_companies.sales_staff`（§1.5） |

| 掲載 / 枠 | `active_jobs_eom / job_posting_limit` | `cms_company_monthly.active_jobs_eom`、`job_posting_limit` | ステップ 08。`job_publish_history` を `pcm` で企業に紐付け、`job_key = COALESCE(jobs_all.set_id, job_id)`。基準日 `as_of` = 過去月は `LAST_DAY(month)`、当月は `run_date`。`job_publish_start_date <= as_of` かつ `(job_publish_end_date IS NULL OR >= as_of)` の `COUNT(DISTINCT job_key)`。枠は §1.5 |
| 閲覧 | 件数 | `cms_company_monthly.job_views` | ステップ 07 → 11。`member_job_detail_views` を `pcm` で紐付け、`DATE(viewed_at)` ごとに `COUNT(DISTINCT view_id)` を取り、月で SUM。**閲覧レコード（view_id）の数で、会員数ではない**（会員数は `job_view_members` に別途ある。§7） |
| 応募 | 件数 | `cms_company_monthly.applications` | ステップ 06 → 11。`member_applications` を `pcm` で紐付け、`DATE_TRUNC(DATE(applicated_at), MONTH)` ごとの `COUNT(*)`。求人応募（`application_type = '求人'`）と企業への直接応募（`'企業'`）の両方を含む |
| 送信 / 枠 | `scout_sent / scout_limit` | `cms_company_monthly.scout_sent`、`scout_limit` | ステップ 05 → 11。`scouts` を `pcm` で紐付け、`DATE_TRUNC(DATE(sent_at), MONTH)` ごとの `COUNT(*)`。自動スカウト（`is_auto_scout`）も含む。枠は §1.5 |

## 4. 企業ページ（`/companies/:id`）

API `GET /api/companies/:id?month=<終了月>`（`src/worker/routes/companies.ts` → `companyService.ts`）。`cms_company_master` 1 行（`accounts_json` / `jobs_json` を含む）+ `cms_company_monthly` の企業全体（`account_type = '__ALL__'`）14 行 + 種別ごとの行（`accountMonthly`）+ `cms_company_login` 1 行を返す。属性の内訳は別 API `GET /api/companies/:id/attributes?from&to&account`（§4.5）。

**期間とアカウント**（2026-10-30〜）: ヘッダの開始月〜終了月（`from` / `to`。窓の 14 か月から。既定 = 契約開始月（窓より前なら窓の先頭）〜当月）と、アカウント種別（全体 / 直接 / 紹介 / 派遣。複数種別のプロファイルを持つ企業だけ切替が出る）で、実績・推移・円グラフがすべて切り替わる。合算の対象月 = `from`〜`to` のうち契約期間に入る月。種別を選ぶと値の元が `cms_company_monthly` の `account_type = <種別>` の行（ステップ 11。facts の `account_type` = 送信 / 応募 / 閲覧 / 求人のプロファイルの種別）になる。ブラウザ側の合算は `src/app/features/company/companyModel.ts`。

### 4.5 円グラフ（誰が求人を見ているか / 誰にスカウトを送っているか）

## 6. 共通ロジックの定義

### 6.1 「興味あり」返信（ステップ 05 `first_interest`）

```sql
SELECT scout_id, MIN(message_sent_at) AS interested_at
FROM `bq-hgt.dwh.scout_histories`
WHERE from_status IN ('質問する', '開封のみ') AND to_status = '興味あり'
GROUP BY scout_id
```

1 スカウトにつき初回の返信日だけを持つ。返信日 `interested_date = DATE(interested_at)`、返信月 `interested_month`。ボード・企業ページの「返信」はこの返信月で数える（`interested_by_reply_month`）。送信月で数える `interested_by_send_month` と `reply_rate`（= 送信月基準の返信 ÷ 送信）はベンチマーク用で画面には出ない。

### 6.2 採用（ステップ 09 `hire_fact`）

| 項目 | ロジック |
|---|---|
| 応募経路 | `member_applications.status = '11.採用'` の行。起点日 = `DATE(applicated_at)` |
| スカウト経路 | `scouts.application_status = '11.採用'` の行。起点日 = `COALESCE(interested_date, DATE(sent_at))` |
| 重複排除 | `(member_id, company_id)` で 1 件。`via_application` / `via_scout` は両方 TRUE になりうる。`member_id` NULL は除外 |
| 帰属月 | `origin_month = DATE_TRUNC(MIN(起点日), MONTH)`。採用が決まった日ではなく、応募 / 返信（無ければ送信）した月に立つ |
| 列 | `hires`（1 人 1 件）、`hires_from_application`（`COUNTIF(via_application)`）、`hires_from_scout`（`COUNTIF(via_scout)`） |

### 6.3 求人の重複排除（set_id）

日本語・英語など複数プロファイルに同じ求人が載るため、`jobs_all.set_id` が同じ求人を 1 件に数える。`set_id` が NULL の求人は `job_id` で数える。`active_jobs`（当日）、`job_publish_history`（月末時点・窓全体）とも `COUNT(DISTINCT COALESCE(set_id, job_id))`。

### 6.4 枠数の優先順位

`companies`（企業単位の契約値）→ `company_profiles` のプロファイル値の MAX → `company_profiles_all` の MAX → 0。D1 `company_settings` の上書きがあれば画面ではそれが勝つ（§1.5）。

### 6.5 CS 担当

`active_companies.sales_staff`（最新スナップショット）→ メール導出 → DA は `'DA'` 固定 → D1 上書き（§1.5）。`owner_source` を `'sf_account_owner'` / `'sf_contract_owner'` に切り替えると SF 取引先 / 契約の所有者（`sf_users`）になる（マートの DECLARE と Worker の `OWNER_SOURCE` を合わせる）。

### 6.6 最終ログイン（ステップ 10 → `cms_company_login`）

| 項目 | ロジック |
|---|---|
| 元 | GA4 の `events_YYYYMMDD`（確定表）と `events_intraday_YYYYMMDD`（速報表）。データセット `analytics_258261950`（旧 CT）と `analytics_553479599`（新 CT） |
| 行の条件 | `event_name = 'get_ID'`。企業 ID は `event_params` の `company_id`（`int_value`、無ければ `string_value` を INT64 に） |
| 日付 | `login_date = DATE(TIMESTAMP_MICROS(event_timestamp), 'Asia/Tokyo')` |
| 取り直し | 毎朝、`run_date − 3 日` 以降の `cms_company_login_daily` を消して確定表から入れ直す。確定表は翌朝 09〜10 時台にできるため、前日分は速報表（`data_date` まで）から入れ、同じ (日, 企業) は確定表を優先。速報値は 3 日以内に確定値に置き換わる |
| 要約 | `last_login_date = MAX(login_date)`、`days_since_login = DATE_DIFF(data_date, MAX(login_date), DAY)`、`login_days_30d` = `data_date − 30 日` より後のログイン日数 |
| 制約 | データは **2026-05-15 以降** のみ。それ以前にしかログインしていない企業は「記録なし」（30 日以上なしと同じ赤）。月次の `login_days` は 2026-05 より前が NULL |

### 6.7 スナップショットの重複排除

`company_profiles`・`member_details`・`active_companies`・`sf_*` は日次スナップショットの積み上げなので、キー（`profile_id` / `member_id` / `company_id` / `Id`）ごとに `ROW_NUMBER() OVER (… ORDER BY recorded_on DESC NULLS LAST)`（SF は `LastModifiedDate DESC`）で 1 行にしてから使う。`sf_*` は `IsDeleted = TRUE` を除く。`companies`・`scouts`・`member_applications`・`member_job_detail_views`・`job_publish_history` は通常テーブルで重複排除しない。
