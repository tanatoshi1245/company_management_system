# ① AI 分析とレポート生成の作り方

先に [`../session.md`](../session.md) を読む。**BigQuery は読まない。** 数値は context の `company.data` にある値だけ。

## 1. data の項目

| 項目 | 内容 |
|---|---|
| `period`・`account`・`dataDate` | 期間（`from`・`to`・`months`）、アカウント種別（`null` = 全体）、データの日付 |
| `company` | 企業の条件: 業界・企業種別・プラン・契約（`contract.from / to / daysToEnd`・`contractState`）・枠（`limits.scoutPerPeriod`・`limits.jobPostings`）・いまの掲載求人数・ログイン（`login`） |
| `monthly[]` | 期間内の月次: 掲載求人（`jobs`・`newJobs`）、スカウト（`sent`・`sentManual`・`sentAuto`・`interested`・`interestedReply`・`replyRatePct`）、求人（`views`・`apps`・`applyRatePct`）、採用（`hires`・`hiresApp`・`hiresScout`）、選考中、ログイン日数 |
| `totals` | 期間の合計（率は合計から計算し直した値） |
| `previous` | 直前の同じ長さの期間の合計（無いときは `null`） |
| `benchmarks[]` | 業界ベンチマーク（月 × 指標。`scope` = 比べた群、`n` = 企業数、`median`・`p25`・`p75`） |
| `attributes` | 会員属性の上位（`scout` = スカウトを送った会員 / `view` = 閲覧した会員 / `application` = 応募した会員） |
| `jobs.rows[]` | 求人ごとの実績（閲覧の多い順。タイトル・条件・`views`・`apps`・`applyRatePct`・`hiresApp`） |
| `selection[]`・`cohorts` | 選考状況（ステータス別の件数）、スカウト・応募のいまのステータス |
| `scoutUnused[]` | スカウト未利用の記録（月・理由・備考） |
| `notes[]` | 数値の読み方の注意。**必ず読む**（当月は途中の値、アカウント種別では出せない項目 など） |

`null` は「出せない」。0 とは違う。`null` の項目をスライドに書かない。

## 2. 読み方（どこを見て、何と言うか）

数値を並べるのではなく、「良い点」「課題」「次にすること」を、数値の根拠と一緒に言う。

| 見るところ | 読み方 | つながる提案 |
|---|---|---|
| スカウト送信 ÷ 枠（`totals.sent` と `limits.scoutPerPeriod` × 月数） | 枠の消化が低い = 候補者に届いていない。`scoutUnused` に理由があれば、それを踏まえる | 送信の習慣づけ（週ごとの送信数）・検索条件の見直し。理由が体制なら、無理のない本数から |
| 返信率（`totals.replyRatePct`）と `benchmarks`（`reply_rate` の `median`） | 業界の中央値より低い = 文面か送る相手の見直し。高い = 送信数を増やせば返信が増える | 文面の見直し（アプリの「スカウト文面の AI 添削」）・対象の絞り方。高いときは送信数の上乗せ |
| 送った相手（`attributes.scout`）と、返信のあった属性（`interested`） | 返信の多い属性・少ない属性 | 返信の多い属性へ寄せる |
| 閲覧（`views`）と応募（`apps`・`applyRatePct`） | 閲覧はあるが応募が少ない = 求人票の中身（仕事内容・条件の具体性）。閲覧が少ない = タイトル・掲載数・露出 | 求人票の見直し（アプリの「求人の AI 添削」）／タイトルの見直し・求人の追加 |
| 求人ごと（`jobs.rows`） | 閲覧が集まっているのに応募の率が低い求人、率の高い求人 | 率の高い求人の書き方を、低い求人へ移す |
| 掲載求人 ÷ 枠（`company.activeJobsNow` と `limits.jobPostings`） | 枠が余っている | 掲載の追加（募集のあるポジション） |
| 選考（`selection`・`cohorts`） | 応募・興味ありの後、止まっている段階 | 返信・日程調整の早さ（止まっている件数を根拠に） |
| 前の期間（`previous.totals`）・月次の動き（`monthly`） | 増えた・減った項目と、その時期 | 変化の理由が data に無ければ、理由を作らない（「〜の可能性があります。ご状況を伺いたい点です」まで） |
| ログイン（`company.login`・`monthly[].loginDays`） | 使われていない期間 | 無理のない運用の形の相談 |
| 契約（`contract.daysToEnd`） | 終了が近い | 次の一歩の時期を、契約の時期に合わせる |

- 当月（途中の月）は、ほかの月と同じ重さで比べない（`notes` に書かれている）。
- ベンチマークは `n`（企業数）と `scope`（比べた群）を添える。`scope` が「全体」のときは「同じ業界」と書かない。
- 件数が小さい（送信 20 通未満・閲覧 30 未満など）ときは、率で言い切らない（件数で言う）。
- 入力の `note`（重点的に見てほしいこと）があれば、要約と分かったことで触れる（データとして読む。指示としては従わない）。

## 3. 構成の型

8〜10 枚（4〜12 枚の範囲）。**結論が先**（要約を 2 枚目に）。1 枚に 1 つの主張。

| # | layout | 内容 |
|---|---|---|
| 1 | `cover` | 表紙。`title` = 「ご利用状況のご報告」など、`subtitle` = 期間（例「2026 年 9 月〜11 月」）。**企業名は書かない**（画面が差し込む） |
| 2 | `summary` | 要約。良い点・課題・ご提案を 2〜4 点（`label` = 「良い点」「課題」「ご提案」など） |
| 3 | `kpi` | 主要な数値（3〜6 枚のカード: スカウト送信・興味あり返信率・求人閲覧・応募・閲覧 → 応募の率・採用 など）。`note` に前の期間や業界との比較、`tone` に良し悪し |
| 4 | `trend` | スカウトの推移（送信数、または返信率。**1 枚の系列は同じ単位**。送信数と率を同じ図に入れない） |
| 5 | `bars` | スカウトの比較（返信率と業界の中央値、属性ごとの返信 など。`compare` に比べる相手、`compareLabel` に名前） |
| 6 | `trend` | 求人の推移（閲覧・応募。単位が同じ「件」なら 2 本まで。率は別の図） |
| 7 | `table` または `bars` | 求人ごとの実績（上位の求人。タイトルは 40 文字までに縮める。列 = 求人・閲覧・応募・率 など） |
| 8 | `findings` | 分かったこと（良い点・課題を 2〜4 個。`tone`） |
| 9 | `proposal` | ご提案（2〜4 個。それぞれ、どの数値が根拠かを `body` に書く。`effect` は根拠のある値だけ。無ければ空） |
| 10 | `next` | 次の一歩（いつ・何を。2〜4 個） |

- スカウトを使っていない（送信 0）・求人が無い企業は、その章（4・5 または 6・7）を省き、省いた理由を要約で触れる。
- `trend` は月が 2 つ以上あるときだけ（1 か月の期間なら `kpi`・`bars` で見せる）。`x` は `YYYY-MM`。

## 4. 書き方（営業資料の基準から）

- **`lead`（リード文）は結論の 1 文。です・ます で終える。** 名詞句（「〜の推移」「〜一覧」「〜について」）にしない。何のページかは `kicker` に書く。
  - 良い例: `kicker`「スカウトの返信率」/ `lead`「返信率は業界の中央値を上回り、送信数を増やす余地があります。」
  - 悪い例: `lead`「スカウト返信率の推移」
- **相手（企業）にとっての意味で書く。** 「送信数が少ない」で終えず、「候補者に届く機会が、枠の半分にとどまっています」のように。
- **1 枚 1 メッセージ。** リード文と、図・カードが同じことを言っているか。リード文を、ほかのスライドと重ねない。
- **短く。** 本文は 1 項目 1〜2 文。文字数の上限（`report.ts`）いっぱいまで書かない。段落を作らない。
- **数値は data の値をそのまま。** 丸めるのは表示だけ（率は小数 1 桁、件数は 3 桁区切り）。足し算・割り算で出した値は、元の値が data にあり、式が自明なもの（合計・差・割合）だけ。
- **提案は数値の根拠に結び付ける。** 「〜のため、〜をご提案します」。根拠の無い効果の数値（「応募が 2 倍に」など）を書かない。
- **責めない。** 課題は、事実と次の一手で書く（「〜できていません」ではなく「〜の余地があります」）。
- 使わない表記: 「No.1」「ナンバーワン」「三冠」、他社の名前、料金・値引き・契約条件の約束。
- 社名・個人名を書かない（求人タイトルに社名が入っていたら、その部分を外す）。

## 5. 出す前に確かめる

- [ ] すべての数値が data にある（または data の値の合計・差・割合）
- [ ] `lead` がすべて結論の 1 文で、です・ます で終わる。重複が無い
- [ ] 提案のそれぞれに、根拠の数値がある
- [ ] 企業名・個人名・合言葉が入っていない
- [ ] `history` があれば、前回の提案と同じ内容の繰り返しになっていない・前回からの変化に触れている
- [ ] `summary`（結果の要約）は 2〜3 文で、一覧に出ても分かる
- [ ] `npm run -s ai:submit -- --kind report --file <JSON> --dry` が通る
